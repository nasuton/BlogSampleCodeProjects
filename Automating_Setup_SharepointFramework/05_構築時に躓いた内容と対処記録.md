# 05. 構築時に躓いた内容と対処記録

この環境を構築した際に **実際に発生した順** で、症状・原因・対処・テンプレートでの再発防止策を記録します。
初回セットアップで同じ表示が出たときは、該当項目の「対処手順」をそのまま実行してください。

> 概要だけ知りたい場合は [04_トラブルシューティング.md](04_トラブルシューティング.md) が症状別の索引になっています。

---

## 記録 1. `docker compose build` が失敗する

**症状**

```
failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine;
check if the path is correct and if the daemon is running
```

**原因** Docker Desktop が起動していなかった。

**対処手順**

1. Docker Desktop を起動 (タスクトレイのクジラアイコンが安定するまで待つ)
2. PowerShell で `docker info | Select-String "Server Version"` が表示されることを確認
3. コマンドを再実行

---

## 記録 2. コンテナが起動直後に落ちる

**症状**

```
exec /usr/local/bin/docker-entrypoint.sh: no such file or directory
```

**原因** Windows で作成したシェルスクリプトが CRLF 改行になっており、shebang 行 `#!/bin/bash\r` が解釈できなかった。

**対処手順**

```powershell
Get-ChildItem docker\*.sh | ForEach-Object {
  $c = (Get-Content $_.FullName -Raw) -replace "`r`n", "`n"
  [IO.File]::WriteAllText($_.FullName, $c, (New-Object Text.UTF8Encoding $false))
}
```

→ **Rebuild Container**

**再発防止** `.gitattributes` に `*.sh text eol=lf` を追加。`New-SpfxProject.ps1` はコピー後に自動で LF 変換する。

## 記録 3. コンテナ内で `npm install` が権限エラー

**症状**

```
npm error The operation was rejected by your operating system.
npm error It is likely you do not have the permissions to access this file as the current user
```

**原因** `node_modules` 用の名前付き volume が初回作成時に root 所有で作られ、`node` ユーザーで書き込めなかった。

**対処手順 (単発)**

```powershell
docker compose run --rm -u root spfx chown -R node:node /usr/app/spfx/node_modules
```

**再発防止** `docker/entrypoint.sh` が起動時に root で volume の所有権を確認・修正してから `node` に降格するようにした。

## 記録 4. `npm install` が `/root/.npm` に書こうとする

**症状**

```
npm error   sudo chown -R 1000:1000 "/root/.npm"
npm error Log files were not written due to an error writing to the directory: /root/.npm/_logs
```

**原因** `setpriv` でユーザーを降格しても `HOME` 環境変数が `/root` のまま残っていた。

**対処** `entrypoint.sh` に `export HOME=/home/node` を追加。**Rebuild Container** で解消。

## 記録 5. ホストから `https://localhost:4321` に繋がらない

**症状** serve のログには `Started Webpack Dev Server at https://[::1]:4321/` と出ているが、ホストの `curl` / ブラウザから `ERR_CONNECTION_REFUSED`。

**原因** Node 22 の名前解決 (`verbatim`) で `localhost` が `::1` (IPv6) に解決され、dev server が IPv6 ループバックにのみバインド。VS Code のポートフォワードや socat はコンテナ内の `127.0.0.1` (IPv4) に接続するため到達できない。

**対処** `NODE_OPTIONS` に `--dns-result-order=ipv4first` を追加。ログが `https://127.0.0.1:4321/` になれば OK。

**再発防止** `Dockerfile` と `docker-compose.yml` の両方に設定済み。

## 記録 6. `.env` を作ったのに `{tenantDomain}` の警告が消えない ★

**症状** serve 起動時に毎回以下が表示される。プロジェクト直下に `.env` を作成し `SPFX_SERVE_TENANT_DOMAIN=xxx.sharepoint.com` を書いてあるのに変わらない。

```
[build:configure-webpack-serve] Placeholder {tenantdomain} was found in serve.json
but OS variable SPFX_SERVE_TENANT_DOMAIN is not set.
Either set the environment variable or update the serve.json initial page url.
```

**原因** `docker-compose.yml` の `environment` は **コンテナ作成時にしか評価されない**。Dev Container を起動した後に `.env` を作成 (または編集) しても、既に動いているコンテナには反映されない。コンテナ内で `echo $SPFX_SERVE_TENANT_DOMAIN` を実行すると空だった。

**対処手順**

1. `.env` がプロジェクト直下 (`docker-compose.yml` と同じ階層) にあり、内容が以下の形式であることを確認
   ```
   SPFX_SERVE_TENANT_DOMAIN=<テナント名>.sharepoint.com
   ```
   (`https://` や末尾の `/` は付けない)
2. VS Code のターミナルを **すべて閉じて新しく開く**
3. 新しいターミナルで `echo $SPFX_SERVE_TENANT_DOMAIN` にテナントが表示されれば OK
4. 表示されない場合は `F1` → **Dev Containers: Rebuild Container**
5. `Ctrl+Shift+B` で serve を再実行 → 警告が消え、先頭に `Workbench URL: https://...` が表示される

**再発防止** `docker/load-env.sh` を追加し、次の 3 箇所で起動時に `.env` を読み直すようにした。これにより **`.env` 変更後はターミナルを開き直すだけ** で反映され、コンテナ再作成は不要。

- `/etc/bash.bashrc` (VS Code の対話ターミナル)
- `.vscode/tasks.json` の `SPFx: serve` タスク
- `docker/serve.sh`

> `New-SpfxProject.ps1` に `-TenantDomain` を渡せば、コンテナ作成前に `.env` が用意されるのでこの問題は起きない。

## 記録 7. ワークベンチで「デバッグ マニフェストを読み込み中にエラー」 ★

**症状** serve は正常 (`Waiting for changes`) で、ワークベンチ URL を開くと以下のダイアログが出る。

```
デバッグのマニフェストを読み込み中にエラーが発生しました。
デバッグスクリプトの読み込み中にエラーが発生しました。
サーバーが実行中で、"debugManifestsFile" パラメーターの URL が正しいことを確認してください

Error: Script error for "https://localhost:4321/temp/build/manifests.js"
https://requirejs.org/docs/errors.html#scripterror
```

**原因** 開発用 HTTPS 証明書 (`certs/rushstack-serve.cer`) が **ホスト側 Windows にインポートされていなかった**。
ブラウザは信頼されていない証明書のスクリプトを黙って読み込み失敗にするため、ワークベンチ側はこの汎用エラーしか出さない。

切り分けで分かったこと:

- ホストから `curl.exe -k` (証明書無視) では `200` → **サーバーもポートフォワードも正常**
- ホストから `curl.exe` (証明書検証あり) は `SEC_E_UNTRUSTED_ROOT` → **証明書の信頼だけが欠けていた**
- コンテナ (Linux) 内で `heft trust-dev-cert` を実行しても OS への信頼登録は行われない (Windows / macOS のみ自動)。ホストで手動インポートが必須。

**対処手順**

1. **切り分け**: ブラウザのアドレスバーに直接 `https://localhost:4321/temp/build/manifests.js` を入力
   - 証明書の警告ページが出る → 手順 2 へ
   - 接続できない → [記録 5](#記録-5-ホストから-httpslocalhost4321-に繋がらない) / serve が動いているか確認
   - JS のソースが表示される → 証明書は OK。ワークベンチを `Ctrl+F5` で再読み込み
2. **証明書をインポート** (どちらか)
   - GUI: エクスプローラーで `certs\rushstack-serve.cer` をダブルクリック → **証明書のインストール** → 保存場所は「現在のユーザー」または「ローカル コンピューター」→ **証明書をすべて次のストアに配置する** → 参照 → **信頼されたルート証明機関** → 完了 (セキュリティ警告は「はい」)
   - PowerShell (管理者):
     ```powershell
     Import-Certificate -FilePath .\certs\rushstack-serve.cer -CertStoreLocation Cert:\LocalMachine\Root
     ```
3. **ブラウザを完全に終了して再起動** (タブを閉じるだけでは証明書ストアが再読込されない)
4. 再度 `https://localhost:4321/temp/build/manifests.js` を開き、鍵アイコンに警告が無く JS が表示されることを確認
5. ワークベンチ URL を開く → **+** → 「ローカル」セクションに Web パーツが表示される

**確認コマンド** (ホスト側 PowerShell)

```powershell
$f = Get-PfxCertificate .\certs\rushstack-serve.cer
Get-ChildItem Cert:\CurrentUser\Root, Cert:\LocalMachine\Root | Where-Object Thumbprint -eq $f.Thumbprint
# 1 件以上表示されればインポート済み
```

**補足**

- 証明書は `~/.rushstack` volume に永続化されるため、コンテナを再作成しても同じ証明書が使われる。インポートは **プロジェクトごとに 1 回**。
  (`docker compose down -v` で volume を消した場合は再生成されるので再インポートが必要)
- 有効期限は 1 年。期限切れ時は **SPFx: trust dev cert** タスクで再生成 → 再インポート。
- Firefox は Windows の証明書ストアを見ないため、Firefox の設定 → 証明書 → 認証局証明書にインポート、または `about:config` で `security.enterprise_roots.enabled = true`。
- 以前ホストに直接 SPFx を入れていた場合、`CN=localhost` の古い証明書が既にストアにあることがあるが、**別の証明書** なので今回の `.cer` を改めてインポートする必要がある。

## 記録 8. 2 つ目のプロジェクトの Dev Container が起動しない

**症状**

```
Error response from daemon: Conflict. The container name "/spfx-dev" is already in use by container "..."
```

**原因** 初期のテンプレートで `docker-compose.yml` に `container_name: spfx-dev` を固定していたため、別プロジェクトと名前が衝突した。

**対処** `docker-compose.yml` から `image:` と `container_name:` の行を削除 → **Rebuild Container**。
compose がフォルダー名から `<project>-spfx-1` を自動採番するため、複数プロジェクトを同時に開ける。

**再発防止** 現行テンプレートでは削除済み。

## 記録 9. bat から PS1 を呼ぶと Docker API に接続できない

**症状**

```
docker : failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine;
check if the path is correct and if the daemon is running:
open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified.
```

**原因** **Docker Desktop が起動していない** (bat 固有の問題ではない)。
Docker CLI は名前付きパイプ `\\.\pipe\dockerDesktopLinuxEngine` 経由でデーモンに接続するが、Docker Desktop 停止中はこのパイプ自体が存在しない。
確認方法: `docker info` が同じエラーになる / `Test-Path \\.\pipe\dockerDesktopLinuxEngine` が `False`。

旧スクリプトは `docker info 2>$null` で起動チェックをしていたが、`powershell -File` で実行すると
ネイティブコマンドの stderr が PowerShell のエラーストリーム (`docker : ...` という書式) として表示されてしまい、
自前の「Docker Desktop が起動していません。」より先に生のエラーが見えていた。

**対処**

1. Docker Desktop を起動してタスクトレイのクジラが安定するまで待ってから再実行する
2. 現行の `New-SpfxProject.ps1` は未起動を検知すると `Docker Desktop.exe` を自動起動し、`docker info` が応答するまで最大 3 分待ってから続行する (`[0/5] Docker Desktop を起動しています...`)
3. bat からは同梱の `New-SpfxProject.bat` を使う (`chcp 65001` + `-NoProfile -ExecutionPolicy Bypass -File` で呼び出し、終了コードを引き継ぐ)

**再発防止** スクリプトの自動起動で解消済み。会社 PC などで `Docker Desktop.exe` のパスが `C:\Program Files\Docker\Docker\` 以外の場合は手動起動が必要。

## 記録 10. bat 実行時にエラーが一瞬出て消える / 内容が確認できない

**症状** bat をダブルクリックするとウィンドウがすぐ閉じる。あるいは `'pasue' は、内部コマンドまたは外部コマンド…として認識されていません` `'#' は…認識されていません` のようなエラーが出る。

**原因**

1. PowerShell 側のエラーが画面にしか出ておらず、ウィンドウが閉じると追えなかった
2. bat を手で編集した際のタイプミス (`pasue`) や、bat では使えないコメント記号 (`#`) が混入した。bat のコメントは `rem` または `::` のみ
3. bat を **UTF-8 で保存すると日本語コメント行が cmd に壊れて解釈される** (`'�' は…認識されていません`)。cmd はシステム コードページ (CP932) でファイルを読むため

**対処**

- `New-SpfxProject.ps1` は `Start-Transcript` で `Doc\logs\New-SpfxProject_<日時>.log` に全出力を記録するようにした。docker / yo の出力は `cmd /c ... 2>&1` 経由で実行し stderr もログに入る。例外発生時は末尾に `==== エラー ====` ブロック (メッセージ・発生行・スタックトレース) を出力して終了コード 1 を返す
- `New-SpfxProject.bat` は終了時に必ず `pause` し、失敗時はログフォルダーのパスを表示する
- bat は **Shift_JIS (CP932)** で保存する。VS Code なら右下のエンコーディング → 「エンコード付きで保存」→ `Japanese (Shift JIS)`

**再発防止** bat を編集したら `cmd` から直接実行して構文エラーがないことを確認する。日本語を含む bat は UTF-8 で保存しない。

## 初回セットアップ チェックリスト

上記を踏まえ、新規プロジェクトで **必ず通る順番** にまとめたものです。

- [ ] Docker Desktop を起動 (記録 1 / 記録 9。スクリプト経由なら自動起動)
- [ ] `New-SpfxProject.ps1 -TenantDomain ...` で作成 → `.env` が先に作られる (記録 6 を回避)
- [ ] VS Code で **Reopen in Container** → `postCreateCommand` 完了まで待つ (`npm install` + 証明書生成)
- [ ] `certs\rushstack-serve.cer` を「信頼されたルート証明機関」へインポート → ブラウザ再起動 (記録 7)
- [ ] ブラウザで `https://localhost:4321/temp/build/manifests.js` を直接開く前に `Ctrl+Shift+B` で serve 起動
- [ ] `https://localhost:4321/temp/build/manifests.js` が警告なしで表示されることを確認
- [ ] ターミナル先頭の **Workbench URL** をブラウザで開き、Web パーツが追加できることを確認
